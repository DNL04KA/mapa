# Расследование churn: что в MAPA переписывается чаще всего

> **О названии.** Здесь *churn* — это **code churn**, текучесть кода по
> истории git, а не отток пользователей. Оригинал skill с таким именем найти
> не удалось, содержимое написано под этот проект. Если имелась в виду
> продуктовая аналитика оттока — скажи, это совсем другой skill.

## Когда применять

Правка в одном файле раз за разом требует правок в соседних; экран оброс
логикой и страшно трогать; планируется рефакторинг и надо выбрать, с чего
начать. Не применять как разовую «уборку»: цель — найти причину, а не
переписать самый длинный файл.

## Почему это работает именно здесь

Файл, который меняли в большинстве коммитов, — это место, где требования ещё
не улеглись. Если он при этом втрое длиннее среднего, каждое следующее
изменение дороже предыдущего. На момент написания skill: 26 коммитов, средний
файл около 155 строк, а `Features/Map/WorldMapView.swift` — 818 строк и
15 коммитов из 26.

## Порядок действий

### 1. Частота правок

```bash
git log --format= --name-only -- '*.swift' \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -20
```

`MAPA.xcodeproj/project.pbxproj` в выдаче игнорируй: он генерируется и
меняется при любом добавлении файла, сигнала в нём нет.

### 2. Наложи размер

```bash
git log --format= --name-only -- '*.swift' | grep -v '^$' | sort | uniq -c | sort -rn | head -20 \
  | while read n f; do [ -f "$f" ] && printf '%3s коммитов %5s строк  %s\n' "$n" "$(wc -l < "$f")" "$f"; done
```

Интересует верхний правый угол: часто меняется **и** большой. Часто и
маленький — нормальная точка роста. Большой и неподвижный — трогать не надо.

### 3. Что меняется вместе

Считать надо **по парам**, а не по точным наборам файлов: на сотне коммитов
каждый набор уникален, и группировка по ним не находит ничего.

```bash
git log --format='%H' | while read c; do
  files=$(git show --format= --name-only "$c" -- 'MAPA' | grep '\.swift$' | sort)
  echo "$files" | awk 'NF' | while read a; do
    echo "$files" | awk 'NF' | while read b; do
      [ "$a" \< "$b" ] && echo "$a + $b"
    done
  done
done | sed 's|MAPA/||g' | sort | uniq -c | sort -rn | head -10
```

Пара файлов, попадающая в один коммит снова и снова, — это один модуль,
разрезанный не по той границе. Это самая ценная находка.

Файл, который стоит в паре с пятью разными, — не модуль, а хаб: через него
проходит всё, и поэтому его правят при любой задаче.

### 4. Прочитай сами коммиты

```bash
git log --oneline -- MAPA/Features/Map/WorldMapView.swift
```

Смотри **почему** его правили. Разные причины (жесты, маркеры, статистика,
локализация) в одном файле — он делает слишком много. Одна и та же причина
снова и снова — решение не доведено до конца.

### 5. Сформулируй диагноз

Для каждого горячего места: что именно в нём смешано, какая граница
нарушена, что вынести. Опирайся на устройство проекта
(`.claude/rules/swift-style.md`): `Core/` без UI, экран в `Features/<Экран>/`,
стиль только из `DS.*`.

## Чего не делать

- Не переписывать код в рамках расследования. Результат — отчёт и план.
- Не считать длину файла дефектом саму по себе: 900 строк вью-модели карты
  могут быть оправданы, если менялись по одной причине.
- Не делать выводов по одному коммиту: нужен повтор.

## Как проверить результат

Отчёт годится, если на каждое утверждение есть цифра из git (сколько
коммитов, сколько строк, какие файлы шли вместе) и предложено конкретное
разделение с указанием, какие именно правки в будущем оно удешевит.
